# TrustForge Skills v0.5.0

FreshPlan v0.5.0 adds freshness-aware dependency graphs and conservative recovery primitives for long-running AI agents.

## Highlights

### Freshness-aware plan graphs

FreshPlan makes time-sensitive evidence explicit. Facts carry provenance plus freshness metadata, and plan nodes declare fact/node dependencies. When evidence becomes stale, FreshPlan invalidates only the affected branch instead of discarding the whole plan.

```text
fact freshness
    ↓
dependency graph
    ↓
selective invalidation
    ↓
refresh evidence
    ↓
minimal plan patch
```

### Three-state freshness model

FreshPlan supports:

- `fresh` — evidence is within its preferred refresh window;
- `refresh_due` — proactive refresh is recommended, but the plan remains valid;
- `stale` — the hard validity bound has passed and dependent nodes are invalidated.

Named freshness policies can define both a soft refresh threshold and a hard expiry:

```yaml
freshness_policies:
  volatile:
    refresh_after_seconds: 300
    expire_after_seconds: 900
```

Existing `ttl_seconds` and `valid_until` fact bounds remain supported. When multiple hard bounds are present, the earliest expiry wins.

### Value-free refresh requests

FreshPlan emits refresh requests containing control metadata, adapter names, opaque references, timestamps, and provenance — not raw fact values.

Application code can register trusted refresh adapters explicitly. The CLI intentionally does not dynamically import adapter modules.

### Replacement evidence and minimal patches

Replacement evidence requires an explicit change classification:

- `changed` — re-plan the affected branch;
- `unchanged` — resume the branch after freshness is restored;
- `unknown` — conservatively re-plan.

FreshPlan emits only the required node operations:

- `blocked`
- `replan`
- `resume`

Unrelated branches remain untouched.

### Performance regression benchmark

The release includes a deterministic synthetic graph benchmark:

```bash
trustforge freshplan benchmark \
  --nodes 1000 5000 10000 \
  --repeats 3 \
  --json
```

CI evaluates a 10,000-node graph and uses a deliberately broad 5-second median threshold as a regression alarm. This threshold is **not a production SLA or performance guarantee**.

## CLI

```bash
trustforge freshplan check --plan plan.yaml --as-of "2026-09-11T09:30:00Z"
trustforge freshplan requests --plan plan.yaml --as-of "2026-09-11T09:30:00Z"
trustforge freshplan patch --plan plan.yaml --evidence replacement.json --as-of "2026-09-11T09:30:00Z"
trustforge freshplan benchmark --nodes 1000 5000 10000 --repeats 3
```

Orchestration gates:

```bash
trustforge freshplan check --plan plan.yaml --fail-on-stale
trustforge freshplan patch --plan plan.yaml --evidence replacement.json --fail-on-replan
```

FreshPlan-related failures use exit code `6`.

## Compatibility contract

FreshPlan v0.5.0 freezes the first public pre-1.0 contract line at schema version `0.1` for:

- FreshPlan documents;
- refresh-request reports;
- replacement evidence;
- plan-patch reports.

Compatibility notes:

- Existing facts using `ttl_seconds` and/or `valid_until` remain valid.
- Named `freshness_policy` references are additive.
- `refresh_due` is non-invalidating; only `stale` evidence invalidates dependent nodes.
- Replacement evidence may omit new TTL/absolute-expiry fields when preserving an existing named freshness policy or existing hard bound.
- `unknown` replacement change remains fail-safe and triggers re-planning.
- Future-dated observations remain fail-closed as stale/suspicious evidence.

Because TrustForge is still pre-1.0, future minor releases may evolve contracts, but incompatible changes must advance the affected schema version and be documented in release notes.

## Security and trust boundaries

FreshPlan is a control-plane primitive, not a source-of-truth validator.

It intentionally does **not**:

- copy raw fact values into freshness reports or refresh requests;
- prove that a caller-selected TTL or freshness policy is appropriate;
- compare domain values to determine `changed` vs `unchanged`;
- automatically execute network refreshes from the CLI;
- dynamically import arbitrary adapter code;
- mutate an external fact store.

Adapter failures, missing adapters, malformed replacement evidence, wrong fact IDs, unknown graph references, cycles, and invalid timestamps fail closed.

## Validation

The release candidate is gated on:

- Python 3.10, 3.12, and 3.13;
- full unit-test suite;
- SkillDiff composite-action smoke test;
- DataLease regression and classifier benchmark gates;
- FreshPlan selective-invalidation gate;
- stale and replan exit-code gates;
- refresh-request and replacement-patch gates;
- refresh-adapter smoke test;
- named freshness-policy gate;
- deterministic 10k-node performance regression gate;
- package/runtime version consistency.

## Known limitations

- refresh adapters are synchronous in v0.5.0;
- there is no built-in persistent state-store adapter;
- freshness policy selection remains caller/domain responsibility;
- performance benchmark shapes are synthetic and not representative of every agent graph;
- runtime integrations with specific agent frameworks are not included yet.
