# TrustForge Skills v0.7.0

CommitmentGuard is the focus of v0.7.0: explicit completion contracts, evidence provenance, freshness/source policy, and first-party evidence collection for common developer workflows.

## Highlights

### Make completion claims explicit

CommitmentGuard v0.7 separates the user's requirements from the agent's confidence. A completion contract can mark commitments as required or optional and resolve each commitment to:

- `PASS` — evidence satisfies the rule;
- `FAIL` — evidence contradicts the rule;
- `UNKNOWN` — evidence is missing, stale, future-dated, untrusted, or cannot be evaluated;
- `WAIVED` — an explicit, still-valid waiver exists.

The overall completion state is:

- `verified_complete` — every commitment passes or is waived;
- `partial` — every required commitment is satisfied but one or more optional commitments remain incomplete;
- `not_verified` — at least one required commitment is `FAIL` or `UNKNOWN`.

```bash
trustforge verify \
  examples/commitmentguard/release-contract.json \
  --evidence examples/commitmentguard/release-evidence.json \
  --as-of "2026-09-11T14:01:00Z"
```

Workflows that explicitly accept optional incompleteness can opt in with `--accept-partial`.

### Preserve evidence provenance

Evidence bundle schema `0.2` records per-observation metadata such as `observed_at` and `source`. Contracts can constrain that evidence through:

- `max_age_seconds` freshness limits;
- `allowed_source_kinds` source allow-lists.

Stale, future-dated, missing-policy metadata, expired waivers, and disallowed sources fail closed to `UNKNOWN` rather than silently becoming proof.

### Collect evidence from commands

```bash
trustforge evidence command \
  --key tests.passed \
  -- python -m unittest discover -s tests
```

Command evidence runs with `shell=False`, bounded timeout, and stdout/stderr redirected away from the evidence bundle. Raw argv is not copied into provenance; the bundle keeps the executable, argument count, argv SHA-256 fingerprint, and exit code.

### Collect normalized pytest evidence

```bash
trustforge evidence pytest \
  --key tests.passed \
  -- tests -q
```

The pytest adapter runs `<python> -m pytest`, maps exit code `0` to `true`, and emits `source.kind: pytest`. Pytest is not added as a TrustForge runtime dependency.

### Collect GitHub Actions evidence without an API token

```yaml
- name: Emit CI evidence
  if: always()
  run: |
    trustforge evidence github-actions \
      --key ci.passed \
      --conclusion "${{ job.status }}" \
      > ci-evidence.json
```

The adapter requires `GITHUB_ACTIONS=true`, whitelists non-secret runtime metadata, does not read `GITHUB_TOKEN`, and makes no GitHub API/network call. Runtime metadata is provenance, not a signed attestation from GitHub.

### Hash JSON artifacts and package manifests

Extract one JSON value with artifact hash provenance:

```bash
trustforge evidence json-artifact \
  --key tests.coverage \
  --input coverage.json \
  --value-path totals.percent
```

Capture an exact package/dependency manifest snapshot:

```bash
trustforge evidence package-manifest \
  --input pyproject.toml
```

The package-manifest observation value is the manifest SHA-256. This can support contracts that require an approved exact snapshot, but the hash does not establish dependency safety or provenance of the manifest producer.

### Detect removed OpenAPI operations

```bash
trustforge evidence api-diff \
  --before openapi-before.json \
  --after openapi-after.json
```

The v0.7 API-diff adapter compares OpenAPI-like JSON path+HTTP-method operations. It emits `true` when no operation was removed and stores only document hashes/counts plus added/removed counts in provenance. Endpoint names are not copied into the evidence bundle.

This adapter is intentionally narrow. Request/response schema changes, parameter changes, auth behavior, semantics, and non-OpenAPI contracts are outside the v0.7 API-diff scope.

## Contract and compatibility

- Python: 3.10+
- CommitmentGuard contract schema: `0.2`
- CommitmentGuard evidence bundle schema: `0.2`
- CommitmentGuard verification report schema: `0.2`
- Legacy nested evidence documents remain accepted.
- Legacy string waivers remain accepted.
- `required` defaults to `true` for compatibility with earlier contracts.
- Existing SkillDiff, DataLease, FreshPlan, and ReproCapsule interfaces remain available.

## Evidence source kinds introduced or normalized in v0.7

- `command`
- `pytest`
- `github-actions`
- `artifact`
- `package-manifest`
- `api-diff`

Source kind is metadata used by policy. It is not cryptographic proof of source authenticity.

## Exit codes

- `0` — successful evidence collection, verified completion, or explicitly accepted partial completion;
- `3` — CommitmentGuard verification did not satisfy the selected completion policy;
- `8` — evidence collection failed.

## Security and trust boundaries

CommitmentGuard v0.7 intentionally keeps the following limits explicit:

- a completion contract can only verify requirements that were actually encoded;
- provenance identifies evidence context but does not cryptographically attest it;
- timestamps can be syntactically valid while coming from an untrustworthy clock/source;
- command/pytest exit status is only evidence about the process that ran;
- GitHub Actions runtime metadata can be useful provenance but is not a signed GitHub attestation;
- artifact/package hashes identify exact bytes but do not prove the producer or dependencies are trustworthy;
- package-manifest hashing does not perform vulnerability or dependency-policy analysis;
- API-diff v0.7 only detects removed path+method operations, not arbitrary breaking API changes;
- `partial` must not be described as full completion;
- waivers must reflect an explicit authorized decision and must not be invented by the agent.

## Upgrade notes

No migration is required for existing TrustForge users. The v0.7 contract/evidence/report schemas are additive alongside the legacy nested evidence path.

The floating GitHub Action ref `v0` should remain pinned to v0.6.0 until the v0.7.0 tag and GitHub release are published and verified. After release verification, `v0` can advance to the v0.7.0 release commit.
